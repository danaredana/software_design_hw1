# ВышКат - учёт парка

Консольное приложение для учёта техники и вещей сервиса кикшеринга «ВышКат».

## Как запустить

```bash
dotnet run --project Console
```

После запуска появляется меню. Можно добавлять транспорт и вещи, смотреть суммарное энергопотребление, список техники для новичков и весь инвентарь.

Тесты:

```bash
dotnet test
```

## Архитектура

Проект разделён на слои:

- **Domain** - сущности (Vehicle, Item) и интерфейсы (IEnergyConsumer, IInventoriable, IBeginnerFriendly)
- **Application** - бизнес-логика (FleetService) и абстракции сервисов
- **Infrastructure** - конкретные реализации (InMemoryFleetRepository, SimpleServiceCenter) и настройка DI
- **Console** - точка входа и интерактивное меню
- **Tests** - юнит-тесты

Такое разделение позволяет менять реализации (например, заменить InMemory-хранилище на базу данных), не трогая домен и сервисы.

## SOLID

Наиболее явно применён **Dependency Inversion Principle**.  
FleetService зависит только от интерфейсов IFleetRepository и IServiceCenter, а не от конкретных классов. Реализации подставляются через DI-контейнер. Благодаря этому в тестах легко подменить техосмотр на FakeServiceCenter.

Также соблюдены:

- **SRP** - у каждого класса одна ответственность. Vehicle хранит данные, FleetService управляет парком, SimpleServiceCenter только решает, принимать технику или нет.
- **OCP** - новые виды транспорта добавляются через наследование от Vehicle, без правки существующего кода.
- **LSP** - любой наследник Vehicle (самокат, велосипед, электровелосипед) можно подставить вместо базового класса, и программа продолжит работать корректно. Формально, сейчас принцип выполнен, но в дальнейшем это может поменяться.
- **ISP** - интерфейсы маленькие и раздельные: IEnergyConsumer, IInventoriable, IBeginnerFriendly. Класс реализует только то, что ему реально нужно.

Сознательно ограничен **Interface Segregation** в одном месте: не стал дробить интерфейсы ещё сильнее. Vehicle реализует сразу три интерфейса - для текущего размера проекта это нормально. Если бы обязанностей стало намного больше, тогда уже стоило бы пересмотреть.

## Расширение

Если добавить новый вид транспорта (например, электросамокат с другим поведением), достаточно создать новый класс-наследник Vehicle. Существующий код менять не нужно.

Если понадобится учёт сотрудников или склада запчастей - придётся добавлять новые сущности и, скорее всего, новые сервисы. Текущий FleetService при этом не сломается, потому что он отвечает только за парк техники и вещей.

## Тесты

Тесты проверяют поведение:

- TryAddVehicle принимает или отклоняет технику в зависимости от решения техосмотра
- GetBeginnerFriendlyVehicles возвращает только устройства с оценкой ≥ 6
- Суммарная энергия считается правильно
- Инвентарь содержит и технику, и вещи

Зависимость техосмотра подменяется через FakeServiceCenter. Это обычный fake: он запоминает, какие машины приходили на осмотр, и возвращает заранее заданный результат (принять всё / отклонить всё). Благодаря DI FleetService даже не знает, что работает с подделкой.
